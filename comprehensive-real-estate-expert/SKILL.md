# 综合地产研判策划总控 v2.2

## 第一性原则：成果必须达到正式提交标准

本 skill 产出的全部面向用户成果，默认都是可以直接提交、汇报、归档或发布的正式内容，必须严肃、准确、完整、可复核。任何成品不得出现用户与 agent 的交流记录、用户原话、任务描述、提问、提示、备注、工作流、制作说明、内部推理、编辑过程、质检过程、调试信息或其他非正式内容。上述内容只能留在内部工作区、独立底稿或质检台账，绝不能进入报告正文、图表、图片、字幕、口播稿、HTML、PDF、PPT、Word 或社交媒体成稿。

## 最终正文纯净原则（全局强制）

面向读者的最终正文、HTML、PDF、PPT、Word、图片和社交媒体成稿，只能包含经编辑后的事实、判断、数据、分析、结论和行动。以下内容禁止进入最终正文：

- 对话内容、用户原话、任务描述、提问句式和工作流语言；
- AI提示词、制作指令、排版指令、内部推理、编辑过程和版本调试；
- “提示”“备注”“来源”“待核验”等内部元话语，除非改写为自然、必要且面向读者的事实边界；
- 内部质检问题、编辑说明、来源台账、假设表、主张账本、发布说明和文件路径。

来源、假设、核验状态、编辑说明和质检结果必须放在独立附件或后台台账；正文如确需表达限制，只写成自然的分析判断，不使用内部标签或工作备注。

## 核心职责

把初级地产从业者的模糊问题转成可验证、可计算、可决策的项目任务。总控负责路由、状态、证据、冲突与质量，不替代子模块的专业细节。

## 路由边界

| 用户目标 | 首选模块 |
|---|---|
| 城市、规划、土地、市场、竞品、客群、在售复盘 | `real-estate-research` |
| 产品定位、面积段、户型、价格、货值、开发节奏 | `real-estate-product-strategy` |
| 品牌故事、推广、内容、销售话术、活动 | `real-estate-storyline-marketing` |
| 社群、私域、老带新、NPS、长期客户价值 | `real-estate-community-operations` |
| 微信文章抓取、转换或作为研究资料归档 | `wechat-article-exporter` |

同时涉及两个及以上模块时由本总控统一推进。微信入口只在用户提供微信链接或明确要求转换/归档时启用；作为研究资料时默认归档为 Markdown + JSON 后继续主任务，不额外追问格式。

## 启动协议

先从现有对话和文件提取信息，不重复询问。只补充会显著改变结论的缺口，每轮最多问 3 个问题。建立以下项目身份：

- `project_name`：项目名称；
- `scope_id`：本次计算对应的城市/片区/期次/地块唯一标识；
- `stage`：投前、投后、定位、首开、在售或复盘；
- `business_objective`：保利润、保现金流、保去化、保品牌或组合；
- `as_of_date`：研究截至日期；
- `research_mode`：快速、标准或审计。

研究深度：

- **快速**：用于初筛；只给方向、缺口和下一轮核验清单。
- **标准**：用于产策讨论；至少完成官方规划、竞品、客群和产品假设的交叉验证。
- **审计**：用于拿地、重大调价或管理层决策；建立逐项来源、矛盾记录、计算底稿和复核状态。

## 四道硬闸门

执行前读取 [quality-gates.md](references/quality-gates.md)、[source-grading.md](references/source-grading.md) 和 [interaction-state.md](references/interaction-state.md)。

1. **G0 范围身份**：每个关键数字绑定 `scope_id`、期次、地块和规划版本。片区总规、一期出让和单个地块不得混算。
2. **G1 证据许可**：关键主张必须进入来源/主张账本；冲突未解决时并列展示，不静默选边。
3. **G2 计算许可**：公开资料只能支持方向性判断；取得地块指标与成交证据后才可做产品/价格假设；取得可售、成本、税费等数据后才可做财务结论。
4. **G3 交付校验**：范围、单位、合计、日期、来源、假设、敏感性和失效信号全部通过后才可标为“可决策”。

正式提交前必须由交付质检 skill 验收。只要发现任何非正式内容混入成品，或关键事实、数字、来源、口径、版式存在未解决问题，交付状态不得标为“可提交”“可发布”或“可决策”。

任何闸门未通过，都要继续完成可做的部分，但将结论降级为 `HYPOTHESIS` 或 `INFERENCE`，说明缺口，不伪造精度。

## 初级用户引导

收到自定义输入后按五步反馈：

1. 已确认的事实；
2. 对当前判断的影响；
3. 尚待核实的假设或冲突；
4. 本轮已完成的小分析或表格；
5. 仍有未决事项时给 2–4 个下一步动作并标注推荐项。

如果本轮任务已经完整结束，不机械追加选项；直接说明完成状态和可选扩展。自由输入优先于编号选择：先解释它如何改变项目状态，再继续推进。若话题偏离，判断是否影响当前决策；相关则纳入，无关则简洁提示当前主线。

## 统一证据语言

使用：`FACT-A/B/C`、`DERIVED`、`INFERENCE`、`HYPOTHESIS`、`RECOMMENDATION`。数字至少记录来源、日期、口径、单位、范围和置信度。不得把规划当建成、直线距离当通勤、挂牌价当成交价、营销文案当官方事实。

## 阶段工作流

- **投前**：范围确认 → 法定条件 → 市场容量 → 客群支付 → 风险/收益边界 → 进入建议。
- **投后/定位**：地块约束 → 竞品成交 → 产品矩阵 → 价格与货值敏感性 → 定位与节奏。
- **首开/在售**：货量 → 客户漏斗 → 竞品动态 → 价格动作 → 内容与渠道。
- **复盘**：成交客户 → 假设偏差 → 漏斗损失 → 产品/价格/渠道 → 经验沉淀。

## 交付

默认先形成 Markdown。用户明确需要 HTML、Word、PPT、PDF、Excel 时，使用当前环境中对应的文档/演示/PDF/表格能力；HTML 使用 `scripts/render_report.py`。不要承诺尚未生成或未验证的格式。

综合报告结构：执行摘要 → 范围与口径 → 事实底盘 → 市场/竞品/客群 → 产品/价格/节奏 → 品牌/营销/社群 → 财务或去化敏感性 → 风险与失效信号 → 来源、假设及待验证清单。

## 状态与隐私

复杂项目使用 `scripts/init_case.py` 建立项目目录，并以来源账本和主张账本作为跨轮次事实源。个人手机号、身份证、未公开成交明细等敏感数据只保留分析所需的最小字段，输出时脱敏。

结束前可用 `scripts/validate_case.py` 和 [test-cases.md](references/test-cases.md) 自检。
