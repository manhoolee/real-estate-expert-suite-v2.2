# HOOSLAND 综合地产研判策划专家 v2.2 使用说明书

**作者：** manhoolee  
**版本：** 2.2.0  
**适用范围：** 地产研究、投资研判、产品定位、营销策划、社群运营、报告交付与社交传播  
**交付标准：** 严肃、准确、可复核、可直接提交

## 一、产品定位

HOOSLAND 综合地产研判策划专家是一套面向地产项目全周期的分析与交付 skill 套件。它把模糊问题拆解为可验证的研究任务、可计算的分析模型、可执行的策略动作和可验收的正式成品。

v2.2 在 v2.1 的研究与策划能力之上，增加了独立的文案编辑、视觉设计、交付质检和社交传播工作组，形成从资料到正式提交内容的完整链路。

## 二、第一性原则：全部成果必须正式可提交

本套件产出的全部面向用户成果，默认都不是聊天草稿，而是可以直接提交、汇报、归档或发布的正式内容。

最终报告、网页、PDF、PPT、Word、图表、图片、字幕、口播稿和社交媒体成稿必须满足：

- 事实准确，判断有依据，数字可回查；
- 项目范围、期次、日期、单位和数据口径清楚；
- 结论、风险、动作和限制表达完整；
- 章节采用“结论先行、证据展开”的总分结构；
- 文件实际生成、打开、渲染并完成交付质检。

以下内容严禁进入任何最终成品：

- 用户与 agent 的对话、用户原话和交流过程；
- 任务描述、提问、提示词和内部工作流；
- 制作说明、排版指令、编辑过程和版本调试；
- 内部推理、质检问题、发布备注和待办事项；
- 来源台账、假设表、主张账本等内部管理记录；
- “提示”“备注”“待核验”等内部元话语。

来源、假设、核验状态、计算底稿、编辑记录和质检证据必须作为独立附件或后台台账管理。正文如需表达限制，应改写为自然、正式、面向读者的事实边界。

## 四、如何开始

### 1. 只提供项目和问题

使用者只需提供项目名称、城市、当前阶段、研究截至日期和需要解决的核心问题，即可启动项目分析。系统将根据项目范围和问题类型组织相应的专业分析内容。

### 2. 提供已有资料

可以上传或指定：规划文件、土地出让文件、预售证、成交和销售数据、竞品资料、户型图、价格表、会议纪要、项目复盘材料或宣传文件。

资料越接近原始来源，数字和结论越容易复核。无法确认的资料不得被包装成确定事实。

### 3. 指定正式交付物

可指定以下交付形式：

- 管理层文字报告；
- HTML 离线报告；
- PDF、PPT 或 Word；
- 1080×1440 的六张社交媒体图片；
- 小红书、抖音、朋友圈或公众号正式内容包；
- 研究底稿、来源账本和计算底稿。

若未指定，默认优先交付：管理层摘要、完整分析报告、可视化成品、独立来源台账和交付质检记录。

## 五、项目推进方法

### 第一步：建立项目身份

每个项目先明确：

- `project_name`：项目名称；
- `scope_id`：城市、片区、期次、地块或楼栋范围；
- `stage`：投前、投后、定位、首开、在售或复盘；
- `business_objective`：利润、现金流、去化、品牌或组合目标；
- `as_of_date`：研究截至日期；
- `research_mode`：快速、标准或审计模式。

没有明确范围时，不把片区总量、一期数据、单宗地块和单栋楼数据混在一起。

### 第二步：区分证据层级

报告中的内容分为：

- `FACT`：有来源的确认事实；
- `DERIVED`：由已确认数据计算得到的结果；
- `INFERENCE`：基于事实的分析推断；
- `HYPOTHESIS`：仍需验证的假设；
- `RECOMMENDATION`：面向决策的建议。

规划愿景不写成已兑现配套，挂牌价不写成成交价，宣传信息不写成法定事实，工程计划不写成交付承诺。

### 第三步：执行计算许可

公开资料可以支持方向性判断，但不能在缺少可售面积、成本、税费、融资和销售数据时伪造精确利润。产品、价格、货值和财务结论必须说明公式、输入、假设、敏感性和失效条件。

### 第四步：形成正式成品

分析结果经过正式文案整理、视觉成品制作和交付质量验收后，方可形成可提交、可发布或可决策的正式成果。未完成验收的内容不得以正式成果名义使用。

任何一步不通过，都不能把文件标记为正式可提交成果。

## 六、三种研究深度

### 快速模式

用于初筛和方向判断。输出核心结论、主要机会、主要风险和资料缺口，不给出超出证据能力的精细价格或财务结论。

### 标准模式

用于产策讨论和项目分析。至少完成规划、市场、竞品、客群和产品假设的交叉验证，并给出可执行的产品、价格、营销或运营建议。

### 审计模式

用于拿地、重大调价、投决、管理层复盘和正式归档。建立逐项来源、矛盾记录、计算底稿、假设区间、敏感性和人工复核状态。

## 七、正式报告的结构要求

每个章节采用总分结构：

1. 开头用醒目文字直接给出本章最重要结论；
2. 紧接着列出 2–3 个重点事实、数字、影响或动作；
3. 再展开表格、图表、公式、证据、来源和限制；
4. 结尾明确行动、决策结果或进入下一章的理由。

推荐报告结构：

1. 执行摘要；
2. 项目范围与数据口径；
3. 法定规划与事实底盘；
4. 城市、板块与市场环境；
5. 竞品、客户与支付能力；
6. 产品定位、户配与户型；
7. 价格、货值、去化与推售节奏；
8. 品牌故事、营销与社群运营；
9. 风险、失效信号与应对动作；
10. 最终结论、决策事项和独立来源附件。

## 八、社交媒体六张图标准

用于小红书、抖音图文或朋友圈时，默认输出统一的 1080×1440 px、3:4 竖版图片。

六张图必须能够独立传达报告主要结论的 70% 以上：

1. 总判断；
2. 范围与事实；
3. 项目状态；
4. 产品与客群；
5. 支付与货值；
6. 最终决策与行动。

每页必须有完整判断、关键数字、图表或结构化关系、自然事实边界和行动结果。不能只放图表和几个字，也不能把核心信息留在图片之外的长正文中。

图片中严禁出现对话、提示、备注、工作流、制作说明、来源台账和内部质检文字。来源链接、数据日期和证据等级放在独立台账或发布后台。

## 九、交付质检与放行条件

交付质检是正式提交的硬门槛，不是可选的收尾步骤。

### P0：不通过即阻断

- 正文混入用户与 agent 对话或非正式工作内容；
- 关键数字、项目范围、日期、单位或口径错误；
- 来源无法回查或关键事实没有证据；
- 文件打不开、核心页面缺失或严重误导；
- 图片和页面出现文字重叠、遮挡、溢出、重复渲染或导出裁切。

### P1：修复后才能放行

- 核心图表、结论或承诺影响理解；
- 章节没有结论先行的总分结构；
- 重要限制、适用前提或失效信号缺失；
- 移动端、打印版或投屏版影响核心阅读。

### 正式放行条件

只有所有 P0/P1 关闭，正式性检查通过，文件已经实际生成并打开验证，才能标记为“可提交”“可发布”或“可决策”。

## 十、来源、隐私与版权边界

- 重要数字必须保留来源、日期、范围、单位和口径；
- 研究资料与最终正文分离管理；
- 个人手机号、身份证、客户姓名等敏感信息只保留分析必需的最小字段，并在对外成果中脱敏；
- 第三方模板、代码、图片和字体只在确认许可或明确允许的范围内使用；
- GitHub 公开项目只作为方法参照，不直接复制代码、品牌、文字或素材；
- 本套件的作者标识为 `manhoolee`；第三方参照项目仍归其原作者或权利人所有。

## 十一、典型应用场景

本套件适用于拿地前研判、已拿地定位、首开准备、在售诊断和项目复盘等阶段。使用时应明确项目名称、分析范围、研究截至日期、当前经营目标和期望成果，以便形成可复核的项目判断。

对于综合项目，系统可以统一组织土地、市场、竞品、客群、产品、价格、营销、社群和风险分析；对于单一问题，可以直接进入对应专业领域，避免无关内容扩展。

对于正式报告，系统将研究结果整理为管理层摘要、关键判断、证据分析、策略动作和决策条件，并根据需要形成网页、PDF、演示文稿、文档或移动端图片。

对于传播内容，系统将已经审定的事实和判断转化为适合不同平台阅读的正式文章、图文、口播稿和图片素材，同时保留原有证据边界，不将规划愿景、工程计划或研究假设表达为已兑现事实。
